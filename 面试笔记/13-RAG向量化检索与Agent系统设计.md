## 1. 工业 PDF：图文分离与版面解析，如何保留「文档逻辑结构」？

**难点**：PDF 不是结构化 HTML，多是 **绘图指令流**；「肉眼看」的块顺序 ≠ **存储顺序**。

**常见管线**（可结合开源 Parser + 自研规则）：

1. **版面检测**：用 **目标检测 / 文档专用模型**（LayoutLMv3、DocFormer、或商业 API）得到 **块级 bbox** 与类别：`text / title / table / figure / list / header-footer`。  
2. **阅读顺序（reading order）**：按 **分栏、跨页、绕图** 排序；常用 **XY-cut**、**图模型**（块为节点，邻接关系为边）或 **专用 reading order 模型**。  
3. **逻辑结构**：  
   - **标题层级**（H1/H2）→ 树或 outline；  
   - **表格**：转 **HTML/Markdown 网格** 或保留为 **结构化 JSON**（单元格合并信息）；  
   - **图**：OCR 说明文字 + **caption** 与正文 **超链接** 关系。  
4. **输出**：带 **元数据** 的中间表示（如 JSON：`{blocks:[{type, bbox, text, parent_id, order}]}`），供下游 **切片与检索** 使用。

**面试表述**：「**检测 → 排序 → 结构化 → 带引用锚点**」四步；强调 **阅读顺序** 和 **父子层级** 比单纯 OCR 更关键。

## 2. 多模态检索：视觉与文本如何在向量空间「对齐」？

**目标**：查询可以是 **图 / 文 / 图+文**，库中也可以是 **图 / 文**，希望在 **同一空间** 里 **近邻 = 语义相关**。

**主流做法**：

1. **双塔 CLIP 式**：图像塔 + 文本塔，**对比学习** 拉近配对 `(图, 文)`，推远负对；检索时 **两侧分别编码** 再 **向量相似度**。  
2. **单塔融合**：把图像 patch token 与文本 token **拼序列** 过 **联合 Transformer**（更重，延迟高，精度常更好）。  
3. **后对齐**：各模态先各自 embedding，再学一个 **浅层投影** 到共享空间（数据需求低于从头训大融合模型）。

**工程注意**：工业 PDF 里 **图** 常与 **周围说明文字** 组成语义单元；检索时可 **(图向量 + 邻域文本向量) 融合池化** 或 **多向量表示**（ColBERT 风格 late interaction）减少 **单向量坍缩**。

## 3. 记忆 Agent：提取、压缩、冲突更新；极端情绪如何干预？

**提取**：每轮对话后 **异步摘要**（滑动窗口 + 周期全量摘要）、**实体/任务状态** 结构化写入 **向量库 + 键值记忆**。

**压缩**：  
- **摘要合并**（多段旧摘要再摘要）；  
- **遗忘曲线**：按 **时间衰减 + 访问频率** 保留；  
- **阈值**：记忆条数超上限则 **聚类合并** 或丢弃低分。

**冲突更新**：  
- **时间戳 + 来源优先级**（用户明确陈述 > 推断）；  
- **显式版本字段**：`fact_key` 维度的 **last_updated**；冲突时 **新覆盖旧** 或 **保留多版本供检索时展示**。

**极端情绪（不中断对话流）**：  
- **不突然打断模型生成**；在 **下一轮 system 侧** 注入 **安全策略**（降温度、缩短输出、禁止建议危险行为）；  
- **并行**跑 **轻量分类器** 检测情绪 → 触发 **资源推荐话术**（热线、求助渠道）；  
- **流式输出**中可在 **段落边界** 插入关怀句（需产品允许），技术上用 **后处理管道** 比硬断模型更稳。

## 4. 向量化前为什么要切片？不切片会怎样？

**原因**：

- **编码器长度上限**：embedding 模型有 **max tokens**，超长 PDF 无法整篇喂。  
- **检索粒度**：整篇向量 **语义平均化**，**细节检索不到**（「找某一条款」会失败）。  
- **噪声**：过长文本 **主题混杂**，向量 **多峰语义** 被压成一团。

**不切片后果**：截断丢信息、或强行 pooling **召回差**、**latency** 与 **成本** 爆炸。

## 5. 重叠区域（overlap）的作用？比例怎么定？

**作用**：避免 **关键句恰落在切块边界** 被切断，导致 **上下文缺失**；overlap 让相邻块 **共享边界句子**，提高 **召回鲁棒性**。

**比例**：常见 **chunk 长度的 10%～25%**；  
- 法律/条款类 **边界敏感** → overlap **偏大**；  
- 新闻类块内自洽 → overlap **可小**。  
用 **dev 集 recall@k** 扫 overlap 与 chunk_size 的 **二维网格** 最靠谱。

## 6. 稠密向量 vs 稀疏向量：区别与适用搜索

| | **稠密（embedding）** | **稀疏（BM25 / SPLADE 等）** |
|---|-------------------------|-------------------------------|
| **语义** | 同义词、改写、跨语言 **可泛化** | **精确词匹配**、专有名词强 |
| **冷启动** | 要模型与算力 | 规则简单、可解释 |
| **适合** | 「意思相近但用词不同」 | SKU、型号、法条编号、错误码 |

**混合检索（Hybrid）**：`score = α·dense + (1-α)·sparse` 或 **两路召回再融合**，工业界很常见。

## 7. Top-K 过大对生成质量的负面影响

- **噪声文档** 进入 prompt → **注意力分散**、**幻觉拼接**（把多篇 unrelated 揉在一起）。  
- **上下文窗口被占满** → **指令被挤出有效注意力**、回答跑题。  
- **延迟与成本** 上升；模型 **更倾向「摘抄」** 而非综合，易产生 **自相矛盾**。

**实践**：先 **小 K 高阈值**，再用 **rerank** 截断到 **top 3～8** 给 LLM。

## 8. 余弦相似度 vs 欧氏距离（文本向量）

**余弦**：看 **方向**，对 **向量长度** 不敏感（若 embedding 已 L2 normalize，余弦与欧氏 **单调相关**）。适合 **语义方向** 主导的场景。

**欧氏**：看 **绝对距离**；若向量 **未归一** 且范数与 **文档长度** 相关，欧氏可能被 **长度偏置** 干扰。

**面试**：「**归一化后 dense 检索常用内积/余弦**；未归一时要小心 **长度陷阱**。」

## 9. 初筛召回后为什么加 Rerank？解决向量检索哪些局限？

**向量召回局限**：  
- **语义近似 ≠ 任务相关**（近邻但答非所问）；  
- **多条件约束**（时间、权限、产品型号）**弱**；  
- **长文档块内** 只有一小句相关，**整段向量** 仍可能排不进前 K。

**Rerank（交叉编码器 cross-encoder）**：`query + doc` **一起进模型** 打相关分，**精度高**、**延迟高**，故放 **第二阶段**，只对 **几十～几百条** 候选排序。

## 10. 文档局部更新：如何做增量索引？

**思路**：每个 chunk 带 **`doc_id`、`chunk_id`、`content_hash`、`version`**。

- **检测变更**：diff 或块级 hash；**仅对变更块** 重算 embedding。  
- **索引侧**：先 **delete-by-query**（`doc_id`+`chunk_id`）再 **upsert**；向量库需支持 **按 id 删除**（Milvus/PGVector/Elasticsearch hybrid）。  
- **一致性**：**双写** 或 **消息队列** 异步索引 + **最终一致**；线上查询可 **短 TTL 缓存** 失效。

## 11. RAG 生成阶段：Prompt 里如何设边界防「没搜到还瞎编」？

**协议化**（示例要点，非唯一模板）：

1. **系统指令**：「仅使用下方 **【检索结果】** 中的内容作答；若 **不足以回答**，必须输出固定短语：`根据已检索资料无法确认`**。  
2. **空检索分支**：若 `【检索结果】` 为空，**禁止**引用不存在来源；可要求 **只输出澄清问题**。  
3. **引用锚点**：要求 `[n]` 与检索块一一对应，后处理 **校验引用号存在**。  
4. **温度**：无检索或低置信时 **降低 temperature / 拒答**。

**仅靠 prompt 不够**：要 **后处理校验**（引用号、与 chunk 的 **n-gram 重叠**、**NLI 蕴含**）叠一层。

## 12. HyDE（Hypothetical Document Embeddings）原理与优势

**原理**：用户问题 **模糊** 时，先让 LLM **生成一篇「假设的理想答案文档」**（不必真实），再对该 **假设文档** 做 embedding，用 **假设向量** 去检索 **真实文档库**。

**直觉**：**查询侧语义被扩写** 后与 **真实文档** 的 **词汇与结构** 更对齐，缓解 **query-doc 分布 gap**。

**优势**：短问、抽象问、**口语与书面语** 差异大时 **召回提升明显**。

**代价**：多一次 **LLM 调用**；假设文可能 **带偏见** 引入 **错误检索方向**，需 **阈值与 fallback**。

## 13. 超长上下文模型出现后，RAG 还有必要吗？

**结论**：**仍然有必要**，但形态会演变。

**RAG 仍强**：  
- **私有/实时数据** 不进权重；  
- **成本**：全量塞上下文 **贵**；  
- **可解释与合规**：引用 **可追溯**；  
- **长文 ≠ 全 relevant**：注意力仍可能 **稀释**，**精选片段** 往往更稳。

**变化**：窗口变大后，**粗排 + 小 K** 可能足够；**Agentic RAG**（多跳、工具）更重要。

## 14. 场景题：两份故障手册冲突，如何优先时效？

**检索后逻辑**（可画流程口述）：

1. **结构化抽取**：从每份 chunk **解析文档标题、版本号、修订日期、适用机型**（规则 + LLM 抽取 JSON）。  
2. **时效比较**：若有 **明确日期/版本号** → **较新者优先**；若只有一条有日期 → **有日期者胜**。  
3. **呈现策略**：模型输出 **分两段引用**，并显式说「**A 写于 x，B 写于 y，已采用较新者**」；若 **无法比较时效** → **列出冲突并请用户确认上下文**（设备型号、区域）。  
4. **系统层**：知识库维护 **`valid_from/valid_to`**，检索时 **自动 filter**。

## 15. 如何解决 RAG「信息覆盖率低」、幻觉、逻辑计算问题？

三者根因不同，**不要指望单一「加大 context」** 解决。

### 15.1 信息覆盖率低（该召回的没进来）

**原因**：chunk 过大/过小、embedding 与 query 分布不一致、只稠密不稀疏、元数据过滤过严、索引滞后。

**手段**：

- **切片与 overlap** 调参 + **多粒度索引**（段落 + 句子窗口）。  
- **Hybrid 检索**（BM25 + dense）+ **query 改写 / HyDE**（见上文）。  
- **多路召回**：不同 embedding、不同字段（标题加权）。  
- **评测**：离线 **recall@k**、**nDCG**；线上 **无结果率**、**点击修正**。

### 15.2 幻觉（尤其是「没检索到仍瞎编」）

**手段**：

- **Prompt 协议**：无检索则固定拒答句式（见第 11 节）+ **引用号强制**。  
- **后处理**：引用与 chunk **重叠度**、**NLI 蕴含**检查。  
- **降低温度 / 拒答策略**；**RAG-only 模式**（关闭无引用自由发挥）。  
- **模型侧**：偏好数据里惩罚 **无依据陈述**（DPO/RL）。

### 15.3 逻辑与数值计算不可靠

**认知**：LLM 不擅长 **精确算术与长推理链** 的可靠闭式解。

**手段**：

- **工具链**：计算器、SQL、Python **沙箱执行**；Agent **先调用再总结**。  
- **结构化中间表示**：让模型输出 **公式 + 变量赋值**，由程序 **求值** 再回填。  
- **分步验证**：代码单元测试、数学 **CAS 校验**（视场景）。

**面试金句**：RAG 解决 **「知道什么」**；**工具与符号执行** 解决 **「算对什么」**；**协议与校验** 解决 **「别编什么」**。

## 小结

- PDF：**版面 → 阅读顺序 → 逻辑树**。  
- 多模态对齐：**对比学习双塔 / 融合塔 + 投影**。  
- RAG：**切片与 overlap 是召回率工程**；**rerank 解决语义近但不相关**；**增量靠 id+hash**。  
- HyDE：**用假设文档拉近 query-doc 分布**。  
- 超长上下文：**不消灭 RAG**，改变 **怎么用**。  
- **覆盖率低 / 幻觉 / 逻辑计算**：见 **第 15 节**（检索与协议 + **工具/执行** 分工）。
