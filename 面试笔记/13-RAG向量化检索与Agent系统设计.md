# 13｜RAG 与向量化检索：从切片到冲突处理

本篇：**RAG 数据流与检索**。Agent 推理模式 / Tool / 强制 JSON → **`15`**；LangGraph/Harness → **`09`**；Prompt/幻觉 → **`09` 第四部分**。

---

## 1. 为什么要切片？重叠干什么？比例怎么定

**不切片的后果**：超过编码器上限要硬截断；或整篇 embedding **语义被平均** → **细粒度检索召回差**；成本与延迟也高。

**重叠（overlap）**：相邻块共享边界句子，避免 **关键句恰被切断** 导致两边都检不到。常见 **chunk 长度的 10%～25%**；条款/法条类偏大，新闻类可小。用 **dev 集 recall** 扫网格比拍脑袋稳。

### 面试怎么答

「切片控粒度与上限；重叠保边界召回；比例用离线 recall 调。」

### 1.1 切片策略：固定窗口 vs 语义边界

- **固定字符/token 窗口 + overlap**：实现简单；缺点是在 **句子/条款中间** 切开 → 召回时 **半句话块** 多。  
- **结构感知（Markdown/标题/PDF 块）**：按 **章节、条款号、表格行** 切，chunk 内 **语义闭合** 更好，适合 **法规/手册**。  
- **语义切（embedding 相似度突变当边界）**：更贵（要先算或小模型断句），适合 **长叙述文**。

**面试话术**：「先结构后语义；overlap 防边界丢召回；用 held-out query 集扫 chunk 长度与 overlap。」

## 2. 稠密向量 vs 稀疏检索（BM25 等）

- **稠密 embedding**：语义相近但词面不同也能近，适合 **口语问书面库**。  
- **稀疏（BM25 等）**：关键词、型号、SKU 强。  
**Hybrid**：两路召回再融合，工业很常见。

### 2.1 双塔是啥？余弦、欧氏又各是啥？

**双塔（Two-tower / bi-encoder）**：**两座塔 = 两个编码器（或两条前向路径）**——  
- **Query 塔**：把用户问题（或改写后的 query）编码成一个向量 **`q`**。  
- **Doc 塔**：把每个文档块（chunk）编码成一个向量 **`d`**。  

检索时 **不把 query 和全文一起送进同一个大模型**（那样对每个 doc 都算一遍，库百万级会爆）。而是 **离线**先把所有 `d` 算好存进向量库；**在线**只算一次 `q`，再在库里找 **和 `q` 最「近」的 `d`**。这个「近」就是下面两种度量之一（或变体）。

**余弦相似度（cosine）**：看 **`q` 与 `d` 两个方向夹角有多小**（方向越一致越像）。  
\[
\cos(q,d) = \frac{q\cdot d}{\|q\|\,\|d\|}
\]  
若两边都做了 **L2 归一化**（长度都变成 1），则 **`cos(q,d) = q·d`**，只剩 **点积**。

**欧氏距离（Euclidean）**：看 **高维空间里两点直线距离多远**，距离小则越近：  
\[
\|q-d\|^2 = \|q\|^2 + \|d\|^2 - 2\,q\cdot d
\]  
若 **`q`、`d` 都已 L2 归一**，则 `\|q\|=\|d\|=1`，上式变成 **`||q-d||² = 2 - 2(q·d)`**。  
所以对一批候选文档来说：**`q·d` 越大 ⇔ `||q-d||` 越小`**——**按余弦排序 与 按欧氏距离排序 会得到同一顺序**（面试就说「归一化后两者单调等价」）。

**工程上为何常写「矩阵乘」**：归一化后排序键就是 **`q·d`**，一整库 `d` 排在一起就是 **`q @ D^T`**（`D` 是所有 doc 向量堆成的矩阵），方便 GPU 与 ANN。

**不归一化时**：`q·d` 会同时受 **夹角** 和 **向量长度** 影响——长向量点积容易更大 → **长文档偏置**；这时余弦与欧氏 **不再等价**，一般要 **归一化** 或 **训练里做长度校准**。

**嵌入模型选型**：同一 pipeline 内 **query 与 doc 必须同一套训练约定**（对称双塔或明确 asym 双塔）；**换模型必须重刷索引**。

## 3. Top-K 太大、余弦 vs 欧氏、为何要 Rerank

**K 太大**：噪声 chunk 进 prompt → **注意力稀释、胡拼多文、延迟成本涨**。实践：**召回可大，精排后喂 LLM 常小（个位数）**。

**余弦 vs 欧氏**：向量常先 **L2 归一**，此时余弦与欧氏单调相关；不归一时欧氏可能被 **向量长度（如文档长短）** 带偏。

**Rerank**：双塔召回快但粗；**交叉编码器（cross-encoder）** 把 query+doc 一起喂模型打分 **准但慢**，只做 **几十～几百候选**。

### 3.1 Rerank 一般用什么（选型口径）

- **Cross-encoder（最常见）**：query 与 doc **拼在一起**（或 `[CLS] query [SEP] doc`）过 **同一套 Transformer**，输出 **相关性分数**。比双塔 **更准**，因 **全交叉注意力**；代价是 **不能离线给 doc 单向量**，只能对 **候选列表** 逐条或 batch 打分。  
- **开源/常见族**：面向 **英文检索/MS MARCO** 训的 cross-encoder 很多；中文/多语场景常用 **BGE-Reranker**、**jina-reranker**、**bce-reranker-base** 等（名字随社区更新，面试说 **「cross-encoder 系、按 held-out 检索集选」** 即可）。  
- **monoT5 / 生成式 rerank**：把「是否相关」做成 **生成式 yes/no 或打分**，效果强但 **更慢、工程更重**，多用于 **精排或竞赛**。  
- **商业 API**：部分云厂商提供 **Rerank API**（输入 query + 候选文本列表），适合快速上线；成本与 **数据出境** 需评估。

### 3.2 怎么「保证」检索比纯 Embedding 准？

**不能保证在任意 query 上恒成立**：rerank 也是学出来的模型，会 **误判、过拟合分布、对长文本截断敏感**。工程上做的是 **在目标分布上可验证地变好**：

1. **离线指标**：同一批 query，对比 **Recall@K / nDCG@K / MRR**（或业务定义的「找对 chunk 即命中」）；向量召回 vs **向量+rerank** 两条曲线必须 **在同一测试集** 上比。  
2. **两阶段漏斗**：**召回宽**（如 ANN 取 50～200）→ **rerank 取 Top 5～20** → 再可选 **LLM 选段**；把「准」压在 **rerank 负责的子集** 上，而不是单靠 embedding 排序。  
3. **Hybrid**：稠密 + BM25 先融合，再 rerank，**专有名词/型号** 场景常明显收益。  
4. **数据对齐**：embedding 与 rerank **域要匹配**（代码库 vs 客服话术）；跨域要 **微调或换模型**，否则 rerank 也可能瞎自信。  
5. **线上**：A/B 或 shadow traffic，看 **引用正确率、用户采纳、人工抽检**；设 **低置信阈值** 时 fallback（扩召回、拒答、换关键词）。

### 面试怎么答

「两阶段：向量召回宽，rerank 收窄；K 大害的是生成阶段信噪比。」

## 4. 增量索引：文档改了，向量库怎么更新

### 4.1 先分清两件事：建库 vs 维护

**第一次建索引（全量）**：把知识库里的 PDF/网页/工单 **切成 chunk** → 每个 chunk 用 **嵌入模型** 算一个向量 **`d`** → 连同 **原文、元数据** 一起 **写入向量库**（如 Milvus、pgvector、Elasticsearch dense_vector）。这一步叫 **全量索引 / 冷启动**。

**上线之后**：文档会 **增删改**——修了故障手册一页、删了过期公告、新上传了产品说明。若每次改动都 **整库重算 embedding、整库重建**，库一大就 **慢、贵、还影响线上检索**。  
**增量索引** 要回答的就是：**只处理「变了的文档/块」**，让检索结果 **尽快跟上最新内容**，而不是 nightly 全量重刷。

### 4.2 核心对象：chunk 是什么、为什么要带那些字段

**chunk**：切片后的一小段文本，是向量库里 **最小检索单位**（见 §1）。一条原始文档通常对应 **很多个 chunk**。

每个 chunk 在库里除了 **向量 `d` 和原文 text**，工程上还会存 **元数据字段**（方便更新、去重、排错）：

| 字段 | 含义 | 干什么用 |
|------|------|----------|
| **`doc_id`** | 哪一篇源文档（如 `manual_v3.pdf`） | 文档级删除、按文档批量失效 |
| **`chunk_id`** | 该文档内第几块（如 `doc_id#7`） | **精确定位** 要更新/删除的那一条向量 |
| **`hash`（内容指纹）** | 对 chunk 正文算 MD5/SHA 等 | 判断 **正文有没有变**；没变就 **跳过** 重算 embedding |
| **`version` / `updated_at`** | 业务版本号或时间戳 | 冲突手册 **取新**、审计、回滚 |

没有 `chunk_id`：你只能「删整篇 doc 再全插」，**改一个字也要重嵌几百块**。  
没有 `hash`：你不知道块是否真变了，容易 **重复嵌入浪费算力**，或 **漏更新**。

### 4.3 「变更」和「重嵌入」分别指什么

**变更（change）**：源文档在 CMS/对象存储里 **新增、修改、删除**。流水线通常：

1. **监听** 文档事件（Webhook、定时扫 S3、Git commit 等）。  
2. **重新切片** 该 `doc_id`（或只 diff 改动的段落，高级做法）。  
3. 对每个新 chunk 算 **hash**，和库里旧 hash **对比**。

**重嵌入（re-embed）**：仅对 **内容 hash 变了** 的 chunk，再跑一遍 **Doc 塔嵌入模型**，得到 **新的向量 `d'`**。  
**没变的块**：**不要** 重算 embedding（省钱）；库里 **保留原向量** 即可。

**删除**：源文档删掉 → 按 `doc_id` **删掉该文档下所有 chunk 的向量**（向量库的 delete by filter）。

### 4.4 索引侧怎么写：delete + upsert，不是「原地改向量」

多数向量库 **不支持** 像改数据库行那样 **原地改向量维度内的浮点数**；常见模式是：

- **按 `chunk_id` 先 delete** 旧记录（或标记 `deleted=true` 的软删）。  
- **再 insert/upsert** 新记录：`{chunk_id, text, d', hash, version, ...}`。

这叫 **按 id 删除再 upsert**。同一 `chunk_id` 在索引里 **始终只有一条有效向量**，避免 **旧向量和新向量并存** 导致检索到过期内容。

### 4.5 「队列」和「最终一致」是啥意思

**为什么要有队列**：文档变更往往 **突发、批量**（一次发布 500 篇）。若每次保存都 **同步** 算 embedding + 写向量库，会 **拖慢 CMS、打爆 GPU**。  
做法是：变更事件 **先丢进消息队列**（Kafka、RabbitMQ、Redis Stream、云 SQS 等），**后台 worker** 按自己的节奏消费：**切片 → hash 对比 → 重嵌入 → upsert**。

**最终一致（eventual consistency）**：用户刚点「保存」后 **几秒内**，检索可能仍命中 **旧 chunk**；等 worker 跑完才变成新内容。产品上要接受 **短暂延迟**，或用 **版本号** 在生成侧提示「知识库同步中」。  
面试口径：**增量索引 = 异步、按块更新，不保证秒级强一致，但保证最终会跟源文档一致**。

### 4.6 和全量重建怎么选

| | 全量重建 | 增量索引 |
|---|----------|----------|
| 何时 | 换 embedding 模型、改切片策略、库坏了 | 日常文档增删改 |
| 成本 | 高（全库重算） | 低（只算变了的块） |
| 一致性 | 简单（新库切换） | 要处理删除残留、队列积压 |

**换嵌入模型** 时：旧向量和新模型 **不可比**，必须 **全量 re-embed**（§2 已写「换模型必须重刷索引」）。

### 面试怎么答

「增量索引不是新算法，是工程：chunk 带 doc/chunk id 和 hash，只重嵌改动的块，向量库 delete+upsert，变更走队列异步刷，接受短暂最终一致。」

## 5. HyDE：用「假答案」帮检索（Hypothetical Document Embeddings）

### 5.1 要解决什么问题

**双塔检索**比的是：**用户问题的向量 `q`** 和 **文档块的向量 `d`** 是否接近。  
但真实场景里经常出现 **表述 gap**：

- 用户：**口语、短、含糊**——「空调不制冷了咋办」  
- 知识库：**书面、长、术语**——「故障代码 E03：压缩机过载保护动作条件…」

两边 **词面不同、句式不同**，即使用很好的 embedding，`q` 和真正该命中的 `d` 在向量空间里也可能 **不够近** → **召回偏低**。  
HyDE 的思路是：**别直接用短问句去搜**；先让 LLM 写一段 **「假如知识库里真有答案，那段答案大概长什么样」** 的 **假设文本**，再用 **假设文的向量** 去搜真库。

**HyDE** = **Hypothetical Document Embeddings**（假设文档嵌入）：名字里的 hypothetical 指 **这段答案不必是真的**，只是 **检索用的桥梁**。

### 5.2 一步步数据流（和双塔对照）

**普通 RAG 检索**：

```text
用户 query → 嵌入模型 → q → ANN 在向量库里找最近的 d → 取出对应 chunk 原文
```

**HyDE**：

```text
用户 query
  → LLM 生成「假设性答案段落」h（不要求事实正确，要求风格像库里的说明书）
  → 嵌入模型把 h 编成向量 q_h（有的实现里 query 塔和 doc 塔仍共用，关键是「用来搜的是 h 不是原 query」）
  → 用 q_h 在向量库里 ANN 找最近的 d
  → 把召回的真实 chunk 塞进 prompt，再让 LLM 根据「真证据」写最终回答
```

注意：**最终回答仍应基于检索到的真 chunk**；`h` **不进入** 给用户看的答案里当事实，除非你再做校验。HyDE 只动 **检索第一步**。

### 5.3 为什么有时能变好

假设文 `h` 往往 **更长、更像文档**，和库里的 `d` 在 **语义空间** 里更接近——相当于用 LLM **把口语 query 改写成「伪文档」** 再检索。  
对 **开放域问答、客服口语对政策库、英文 MS MARCO 类** 文献里 HyDE 常有 **Recall 提升** 的报告。

### 5.4 风险和工程兜底（必答，否则像吹魔法）

1. **假设文带偏**：LLM 胡编了一个 **错误方向** 的「假答案」，会把 ANN **拽到错误簇** → 召回来的 chunk 全偏。  
2. **多一次 LLM 调用**：延迟与成本涨；要高 QPS 时要 **缓存** 或 **仅对低置信 query 开 HyDE**。  
3. **和 embedding 训练分布**：`h` 是生成体写的，若和 doc 塔训练语料风格差，收益不稳定。

**常见兜底**：

- **双路检索融合**：原 `query` 一路 + HyDE 一路，**RRF 或加权** 合并候选，一路挂了另一路还能救。  
- **置信度门控**：向量召回 top1 分数已很高则 **不开 HyDE**；分数低再生成 `h`。  
- **HyDE 只用于召回，生成仍强制引用**：配合 §6 的「无依据不编」。

### 5.5 和 Query 改写、Multi-query 的区别（防混）

| 手段 | 在干什么 |
|------|----------|
| **Query 改写** | 把 query 改短/扩词/纠错，仍是一条 **问句** 去嵌 |
| **Multi-query** | 生成 **多个不同问法**，分别检索再合并 |
| **HyDE** | 生成的是 **一段陈述性「假答案」**，用 **答案体裁** 去对齐 **文档体裁** |

### 面试怎么答

「HyDE 是检索增强：先用 LLM 写假设性答案再嵌入去搜真库，缓解口语和书面库的向量距离；要防假设文带偏，常和原 query 双路融合，最终回答仍靠真 chunk。」

## 6. 生成侧：检索到了怎么答、没检索到怎么不编

RAG 的 **Retriever 只负责找证据**；**Generator（LLM）仍可能胡编**——把检索到的 chunk 拼进 prompt 后，模型仍可能 **忽略 chunk、混进预训练知识、编造引用号**。所以生成侧要 **协议 + 校验**，不能单靠一句「请根据上下文回答」。

### 6.1 生成协议（写进 system / 模板）

常见三条 **硬规则**（可组合）：

1. **无依据则拒答**：若检索分数低于阈值、或召回为空，固定输出 **「知识库中未找到依据，无法回答」** 类句式，**禁止**用常识硬答政策/医疗/计费类问题。  
2. **强制引用**：答案里每个事实句带 **`[chunk_id]` 或 `[1][2]`**，与 prompt 里注入的块一一对应；方便后处理与人工抽检。  
3. **只许改写不许新增**：要求 **「答案中的事实必须能在引用块中找到支持句」**（仍可能被绕过，所以要 §6.2）。

### 6.2 后处理校验（runtime，不靠模型自觉）

- **引用存在性**：模型写的 `[3]` 是否在 **本次注入列表** 里；不存在则 **拒发或触发重生成**。  
- **span–chunk 重叠**：用 **关键词重叠、embedding 相似度、或小型 NLI** 判断答案句与对应 chunk 是否 **真有支撑**；重叠过低 → 标红或拒答。  
- **与检索分数联动**：top1 相似度很低时 **即使模型很自信也降级**（拒答 / 仅返回原文摘录）。

约束解码（grammar 强制 JSON、强制 citation 字段）见 **`15` §5.1**、**`09` §4.4**。

### 面试怎么答

「RAG 防幻觉靠三层：检索阈值、生成协议（无依据拒答+强制引用）、后验校验引用是否真在 chunk 里。」

## 7. 超长上下文还会要 RAG 吗

### 7.1 长窗口解决的是什么

把 **128k、1M tokens** 塞进一次 forward，解决的是 **「单次能读多长」**——适合 **整本书、整仓库、长对话历史** 都在 **同一次注意力** 里处理的任务。

### 7.2 为什么 RAG 仍然常见（四个独立理由）

1. **私有与实时数据**：模型权重里 **没有** 你公司昨晚更新的工单、未公开财报；再长的 context 也 **变不出** 没喂进去的数据。RAG/工具是 **接外部数据源** 的通道。  
2. **成本与延迟**：全长 attention 随长度 **近似线性～超线性涨**（还受实现影响）；先检索 **Top-K 小块** 再生成，常比 **整库塞进窗** 便宜一个数量级。  
3. **可解释与合规**：客服/金融要 **「答案出自哪条政策第几段」**；RAG 的 chunk id 比「模型在长窗某处瞄了一眼」好审计。  
4. **「中间迷失」仍在**：标称 1M 不等于 **任意 needle 都检索得准**；实验与产品里 **长窗尾部、中部信息利用率** 仍可能差，**先检索再聚焦** 往往更稳。

### 7.3 面试口径：不是二选一

窗口变大 → **「全量塞窗」方案变可行的情况变多**（例如单文件 QA）；但 **企业知识库、多租户、强引用** 场景里 **RAG + 长窗** 常 **叠加**：长窗放 **会话与少量检索结果**，RAG 管 **海量库**。别说「有了长上下文就不要 RAG」。

### 面试怎么答

「长窗解决能读多长；RAG 解决数据从哪来、贵不贵、能不能引用溯源；很多系统是两者一起用。」

## 8. 覆盖率低、幻觉、算术：三件事别混谈

面试里三个抱怨 **听起来都像「答错了」**，根因和修法 **完全不同**。先 **分型** 再下药。

### 8.1 覆盖率低（检索没召对）

**现象**：该用的手册段落 **根本没进 Top-K**，模型再守规矩也只能 **拒答或瞎编**。

**常见根因**：chunk 切坏（§1）、embedding 与域不匹配（§2）、**只稠密不 BM25** 丢 SKU/型号、索引 **过期**（§4）、query 太口语（§5 HyDE）、**多知识库路由** 错库。

**手段**：离线 **Recall@K / 人工标注「gold chunk」**；调切片与 hybrid；增量索引保新鲜；低分 **扩召回或改写 query**，而不是先怪模型幻觉。

### 8.2 幻觉（召到了或没召到，生成乱说）

**现象**：检索块里 **没有** 某说法，答案里 **却有**，或 **引用号造假**。

**根因**：生成侧 **爱补全**（§6）、温度高、对齐不足、**prompt 没强制只许用证据**。

**手段**：§6 协议 + 校验；降温度；偏好对齐里加 **「有据/无据」** 维度（`05`）；**不要** 用「加大 Top-K」当治幻觉的主药——K 太大反而 **噪声进窗** 诱发胡拼。

### 8.3 算术 / 逻辑（模型不擅精确算）

**现象**：「三段报价加总」「日期差几天」「SQL 聚合」错。

**根因**：LLM 是 **近似模式匹配**，不是 **符号计算引擎**；检索 **帮不上** 精确算术。

**手段**：**工具闭环**——计算器、代码沙箱、SQL 执行器；中间结果 **结构化**（JSON 表）再让模型 **只负责解释**；Agent 里 **Reward 对执行结果二值化**（`15` §6）。  
**Retriever 治不好算术**；别在 RAG 项目上死磕 embedding 来修 **1+1**。

### 对照表（背因果，不背口号）

| 症状 | 先查哪一层 | 典型修法 |
|------|------------|----------|
| 该有文档却没有 | 检索 / 索引 | chunk、hybrid、HyDE、增量索引、Recall@K |
| 有文档但答案胡写 | 生成 / 对齐 | 拒答协议、引用校验、DPO/RLAIF |
| 数字/逻辑错 | 执行器 | tool、代码、SQL，结果回灌 |

### 面试怎么答

「先问是『没找到』还是『找到了乱说』还是『算错了』；前两者动 RAG 与生成护栏，算术必须上工具。」

## 9. 项目口述：工业 PDF 与多模态对齐

### 9.1 为什么「只 OCR 一串字」不够

扫描 PDF 常有 **双栏、页眉页脚、表格、插图说明**。若 OCR 后压成 **一条长字符串**，chunk 会 **跨栏拼接、表头表体分离**，检索时 **语义断裂**。工业管线要 **版面分析（layout）** 再切片。

### 9.2 典型 PDF 管线（按数据流说）

1. **版面检测**：模型或规则标出块类型（标题、正文、表格、图注）和 **bbox**（框坐标）。  
2. **阅读顺序**：按 **分栏、绕图** 排成人类阅读序，避免「左栏末句接右栏首句」。  
3. **结构化输出**：落成 **带父子层级的 JSON 或 Markdown 树**（章 → 节 → 段 → 表），chunk 时 **按标题/条款边界切**（呼应 §1 结构感知切片）。  
4. **入库**：每个 chunk 带 **`doc_id`、页码、章节路径** 元数据，方便引用时写「见手册 §3.2」。

面试强调：**价值在 layout + 结构**，不是「换了个 OCR 引擎」。

### 9.3 多模态向量对齐（图搜文 / 文搜图）

**CLIP 式双塔**：图像 encoder 得 **`v_img`**，文本 encoder 得 **`v_txt`**，对比学习拉近 **配对图文**、推远非配对。检索时 **问句走文本塔**，在 **图像向量库** 里 ANN——适合 **商品图、示意图**。

**融合塔**：图+邻域 OCR 文字 **一起编码** 成一个向量，减轻 **纯图向量语义坍缩**（多张不同图向量挤在一起）。

**和文本 RAG 的关系**：多模态库常 **单独索引**；进 LLM 前仍可能 **转成 caption 或 Q-Former 摘要** 再和文本 RAG 汇合（细节见 **`11`**）。

### 面试怎么答

「PDF 项目讲清 layout→阅读顺序→结构化树→按结构 chunk；多模态讲双塔或图文融合向量，别只背 CLIP 三个字。」

## 10. 记忆 Agent 与极端情绪

### 10.1 Agent 里的「记忆」分三层（别混成一个大词）

| 类型 | 存什么 | 典型实现 | 解决什么 |
|------|--------|----------|----------|
| **工作记忆** | 当前任务相关的最近对话、工具结果摘要 | **上下文窗内**；超长则 **滚动摘要** | 多轮连贯，不占满窗 |
| **长期记忆（语义）** | 用户偏好、历史案件、过往结论 | **向量库** + 按 query 检索注入 | 跨会话「你还记得我吗」 |
| **结构化状态** | 订单号、当前步骤、已选 SKU | **数据库 / JSON state**（LangGraph state） | 精确字段，不靠模型背 |

**压缩**：窗快满时 **后台摘要** 旧轮次；**遗忘策略**（只保留最近 N 条长期记忆、或按重要性打分淘汰）。  
**冲突**：同一键两条记忆矛盾时，用 **时间戳新者优先** 或 **来源优先级**（人工确认 > 模型推断）。

### 10.2 极端情绪用户（产品策略，不是模型玄学）

**不要** 在用户情绪激动时 **硬截断** 生成流（体验差）；常见做法：

- **并行轻量分类**（情绪/风险意图）→ 触发 **关怀话术模板** 或 **转人工/热线**（`09` Harness 里 Verifier/路由思想）。  
- **下一轮 system 注入**：「用户焦虑，先共情再解决问题，避免争论」。  
- **安全护栏**：自伤/暴力等 **固定 escalation**，与 RAG 无关但要 **和 Agent 编排一起设计**。

### 面试怎么答

「记忆分窗内、向量长期、结构化 state；情绪用分类+策略注入+人工升级，别只靠 prompt 骂用户。」

## 11. 场景：两份故障手册冲突

### 11.1 问题设定

知识库里 **同一故障** 有两份手册片段：**2023 版** 写换 A 零件，**2025 版** 写换 B 零件。用户问「不制冷怎么办」，若 RAG **两条都召回** 且生成 **混用**，会出 **危险错误**。

### 11.2 处理流水线（生成前 + 生成后）

**（1）库侧元数据（预防）**  
每个 chunk 带 **`version`、`valid_from`、`valid_to`、`适用机型/区域`**。检索后 **按机型过滤**；若用户未说明机型 → **检索仍可做**，但生成前要 **识别缺口**。

**（2）结构化抽取（比较能否排序）**  
从候选 chunk **抽** 版本号、日期、适用条件。若 **可比较**（2025 > 2023，且机型匹配）→ **优先采用新版** 作主答案，旧版 **footnote 式说明「历史版本曾建议 A」**。

**（3）无法比较时（透明 + 反问）**  
条件 **互斥**（仅适用北美 vs 仅适用欧洲）而用户未说地区 → **不要猜**；输出 **并列两段引用** 并 **明确冲突点**，**反问** 用户机型/地区/购买日期。

**（4）生成协议**  
要求 **「若来源矛盾，必须指出矛盾并请求澄清，禁止静默合并」**。

### 11.3 和 §4 增量索引的关系

手册更新时 **旧 chunk 必须失效**（delete by `doc_id` 或 `version`），否则 **增量索引只做 upsert 不删** 会 **新旧共存**——冲突题在工程上常是 **索引版本没维护好**。

### 面试怎么答

「冲突场景：元数据过滤→能比较取新→不能比较并列引用+反问；库侧 valid_from/version，更新时删旧 chunk。」
