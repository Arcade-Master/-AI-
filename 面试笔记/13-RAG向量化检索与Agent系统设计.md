# 13｜RAG 与向量化检索：从切片到冲突处理

**建议阅读顺序（本篇内部）——按「数据进索引 → 召回 → 排序 → 生成 → 线上坑」**：  
**切片与重叠**（为什么要切）→ **稠密/稀疏向量**（两路召回）→ **Top-K、余弦/欧氏、Rerank**（召回到精排）→ **增量索引**（工程维护）→ **HyDE**（query 侧增强）→ **生成侧防幻觉 Prompt** → **超长上下文会不会干掉 RAG**（宏观判断）→ **三类综合问题：覆盖率低 / 幻觉 / 算术** → **PDF 与多模态项目口述** → **记忆 Agent 与情绪** → **两份冲突手册场景题**。

Agent 通用架构见 **`15`**；纯 Prompt 技巧见 **`09`**。

---

## 1. 为什么要切片？重叠干什么？比例怎么定

**不切片的后果**：超过编码器上限要硬截断；或整篇 embedding **语义被平均** → **细粒度检索召回差**；成本与延迟也高。

**重叠（overlap）**：相邻块共享边界句子，避免 **关键句恰被切断** 导致两边都检不到。常见 **chunk 长度的 10%～25%**；条款/法条类偏大，新闻类可小。用 **dev 集 recall** 扫网格比拍脑袋稳。

### 面试怎么答

「切片控粒度与上限；重叠保边界召回；比例用离线 recall 调。」

### 1.1 切片策略：固定窗口 vs 语义边界

- **固定字符/token 窗口 + overlap**：实现简单；缺点是在 **句子/条款中间** 切开 → 召回时 **半句话块** 多。  
- **结构感知（Markdown/标题/PDF 块）**：按 **章节、条款号、表格行** 切，chunk 内 **语义闭合** 更好，适合 **法规/手册**。  
- **语义切（embedding 相似度突变当边界）**：更贵（要先算或小模型断句），适合 **长叙述文**。

**面试话术**：「先结构后语义；overlap 防边界丢召回；用 held-out query 集扫 chunk 长度与 overlap。」

---

## 2. 稠密向量 vs 稀疏检索（BM25 等）

- **稠密 embedding**：语义相近但词面不同也能近，适合 **口语问书面库**。  
- **稀疏（BM25 等）**：关键词、型号、SKU 强。  
**Hybrid**：两路召回再融合，工业很常见。

### 2.1 双塔打分到底在算什么（面试别只会说「embedding 近」）

**查询向量 `q`** 与 **文档向量 `d`** 多为 **L2 归一化** 后的高维单位向量。此时 **余弦相似度** `cos(q,d) = q·d`（点积）。**欧氏距离** `||q-d||² = 2 - 2q·d`，在归一化下与 **负点积单调相关**——所以 **「余弦 vs 欧氏」在归一化后排序等价**，工程上常直接 **矩阵乘做大库检索**（ANN 索引）。

**不归一化时**：范数大的向量点积容易更大 → **长文档偏置**；要么 **归一化**，要么 **学一个温度/标量校准**。

**嵌入模型选型**：同一 pipeline 内 **query 与 doc 必须同一模型同头部**（或明确 asym 双塔）；换模型要 **重刷索引**。

---

## 3. Top-K 太大、余弦 vs 欧氏、为何要 Rerank

**K 太大**：噪声 chunk 进 prompt → **注意力稀释、胡拼多文、延迟成本涨**。实践：**召回可大，精排后喂 LLM 常小（个位数）**。

**余弦 vs 欧氏**：向量常先 **L2 归一**，此时余弦与欧氏单调相关；不归一时欧氏可能被 **向量长度（如文档长短）** 带偏。

**Rerank**：双塔召回快但粗；**交叉编码器（cross-encoder）** 把 query+doc 一起喂模型打分 **准但慢**，只做 **几十～几百候选**。

### 面试怎么答

「两阶段：向量召回宽，rerank 收窄；K 大害的是生成阶段信噪比。」

---

## 4. 增量索引

chunk 带 **`doc_id, chunk_id, hash, version`**；变更只 **重嵌入改动块**；索引侧 **按 id 删除再 upsert**；用队列保证 **最终一致**。

---

## 5. HyDE

**做法**：对模糊问题先生成 **「假设的理想答案」**（不必真），再 **嵌入假设文本** 去检索真实库。  
**好处**：拉近 **口语 query** 与 **书面文档** 的表述 gap。  
**风险**：假设文可能 **带偏检索方向** → 要阈值与 fallback。

---

## 6. 生成侧：没检索到也别编

协议化：**无检索则固定拒答句式**；**强制引用号**；后处理做 **引用存在性 / 与 chunk 重叠** 检查。单靠 prompt 不够。

---

## 7. 超长上下文还会要 RAG 吗

**要**：私有实时数据、成本、可解释引用、注意力稀释问题仍在。窗口变大改变的是 **「检索还要不要」的比例**，不是 **「RAG 这题消失」**。

---

## 8. 覆盖率低、幻觉、算术：三件事别混谈

| 问题 | 根因方向 | 手段 |
|------|----------|------|
| **覆盖率低** | chunk、embedding、路由、索引版本 | 调切片/hybrid/HyDE/多路召回/看 recall 指标 |
| **幻觉** | 生成模型爱补全、无约束 | 检索协议 + 校验 + 降温度 + 对齐训练 |
| **算术/逻辑** | LLM 不擅精确计算 | **工具**（计算器、SQL、Python 沙箱）、结构化中间结果由程序执行 |

### 面试怎么答

「检索解决『有没有依据』；算术交给执行器；幻觉要协议+校验+模型对齐组合拳。」

---

## 9. 项目口述：工业 PDF 与多模态对齐

**PDF**：检测块类别与 bbox → **阅读顺序**（分栏绕图）→ 输出 **带父子层级的 JSON/Markdown 树**；比「只 OCR 一串字」值钱。

**多模态向量对齐**：CLIP 式 **双塔对比学习** 或 **融合塔**；工业上常 **(图向量 + 邻域文字)** 融合，减轻单向量坍缩。

---

## 10. 记忆 Agent 与极端情绪

**记忆**：工作记忆（窗内摘要）+ 向量长期记忆 + **结构化键值状态**；**压缩**靠周期摘要与遗忘策略；**冲突**靠时间戳与来源优先级。

**情绪**：别硬断模型流；用 **下一轮 system 注入策略**、并行 **轻量分类** 触发关怀话术或资源链接。

---

## 11. 场景：两份故障手册冲突

**结构化抽**版本/日期/适用机型 → **能比较则取新** → 输出里 **并列引用并说明取舍** → 无法比较则 **反问用户上下文**。库侧维护 **`valid_from`** 元数据可自动过滤。

---

## 本篇小结

- 顺着 **索引→召回→精排→生成→维护** 讲，就不散。  
- Retriever 治不好 **算术**；**执行器**才治。  
- 冲突场景展示 **规则 + 元数据 + 透明呈现**。
