# 09｜Prompt、数据、幻觉（产品向）

**建议阅读顺序（本篇内部）**：**Prompt 在工程里扮演什么角色** → **怎么判断好坏** → **few-shot / CoT / 角色提示各解决什么** → **数据清洗与 instruction 构造** → **幻觉的发现与缓解** → **「实际项目」怎么口述才像做过**。

与 **`13`（RAG 系统）**、**`15`（Agent）** 互补：本篇偏 **文本策略与数据**；RAG/Agent 偏 **系统结构**。

---

## 1. Prompt 不是咒语，是「接口设计」

不改权重的前提下，你用 **格式、顺序、示例、禁止项** 去 **缩小模型合法输出空间**。它和 **温度、top-p、后处理** 是一套的。

**怎么算达标**：任务成功率、格式约束通过率、换说法仍稳（鲁棒）。

**怎么评估**：小离线集 + 规则校验；线上影子流量；**prompt 版本与模型版本一起发版**。

### 面试怎么答

「Prompt 是条件分布的工程设计；要版本化、要离线+线上双评。」

---

## 2. Few-shot、CoT、角色提示

- **Few-shot**：用例子 **锚定输出形态**；坏例子会被学走。  
- **CoT**：要求 **中间步骤**，换「更深 effective 计算」；仍可能 **过程胡编**。  
- **角色**：语气与立场软约束；与安全策略冲突时要 **系统层兜底**。

### 面试怎么答

「few-shot 定格式；CoT 买深度；角色定风格；三者都挡不住事实错，事实要靠 RAG/工具。」

---

## 3. 数据清洗与 instruction 构造

**清洗**：去重、去隐私、语言检测、低质过滤、保留文档结构（标题层级）。  
**脏数据**：规则优先 + 小模型质检 + 人审难例；**记录版本号** 可复现。

**instruction 数据**：覆盖 **任务类型 × 难度 × 语言**；与线上一致的 **system / tools schema**；合成数据要 **人审或交叉审**。

---

## 4. 幻觉

**定义**：读起来像那么回事、但 **无依据或与事实不符**。

**发现**：检索对照、可执行检查、多采样一致性、线上点踩。  
**缓解**：RAG、拒答协议、约束解码、工具、对齐训练——**单靠 prompt 不够**。

### 4.1 把「缓解」说成可落地的数据与 loss 口径

- **RAG + 引用链**：生成前注入 chunk；生成后做 **span–chunk 重叠检测**、**引用 id 是否存在**；失败则 **拒答或重检索**，这是 **系统约束** 不是 prompt 玄学。  
- **约束解码**：对「必须输出 JSON / 必须含 citation 字段」用 **grammar**，减少格式胡编（见 **`14`**）。  
- **偏好对齐**：用 **事实性/有据性** 维度做人标或 RLAIF 偏好，走 **DPO/RLHF**（见 **`05`**）——**loss 仍是成对或 RM+PPO**，只是 **标注维度换成「是否胡编」**。  
- **工具闭环**：算术、查库、查实时状态 **必须走执行器**，模型只产 **调用计划**；**reward 可对执行结果二值化**，与 GRPO 友好。

### 面试怎么答

「幻觉要系统：检索证据链 + 后验校验 + 约束解码；对齐里把『有据』当偏好维度训。」

---

## 5. 「实际项目」口述模板

- **清洗**：按来源说规则 + 抽样表 + 版本脚本。  
- **脏数据**：丢弃阈值 vs 修正策略，避免分布塌缩。  
- **instruction**：意图矩阵 + 拒答/澄清负例 + schema 对齐。  
- **幻觉**：离线引用检查 + 线上触发检索/拒答。

---

## 本篇小结

- Prompt/数据是 **行为上界**；幻觉是 **结构性风险**，要系统治。
