# 15｜Agent：上下文、架构、与 LLM 区别、Tool 调用

**建议阅读顺序（本篇内部）**：**Agent vs LLM** → **架构分块** → **ReAct / Plan&Execute / Reflection（并列还是嵌套）** → **上下文与 Tool** → **Agentic RL 与工具 Reward**。

RAG 详见 **`13`**；Prompt 见 **`09`**；GRPO/GSPO 见 **`05`/`12`**。

---

## 1. Agent 和 LLM 差在哪

**LLM**：给定文本条件，输出文本分布。  
**Agent**：以 LLM 为 **决策核**，外挂 **工具执行、记忆读写、状态机编排**，形成 **观察→思考→行动** 闭环。

### 面试怎么答

「LLM 是大脑皮层；Agent 是带手脚和记事本、还能调 API 的系统。」

---

## 2. 典型架构（从上到下）

用户入口 → **编排器（orchestrator，状态机/ReAct 循环）** → **策略模型（LLM）** → **工具执行器（HTTP/DB/代码沙箱）** → **记忆子系统（摘要+向量库+KV 状态）** → **护栏与观测**（日志、trace、配额）。

### 2.0 口语里的 Engine / Subengine（不是统一标准术语）

文档和博客里常把 **整段 Agent 运行时** 叫 **Engine**：把「循环调度、上下文裁剪、tool 路由与超时、重试、计费/trace、终止条件」等 **宿主侧能力** 和 LLM 绑在一起的那层，区别于「裸调一次 ChatCompletion」。

**Subengine** 没有单一权威定义，常见两种指法（面试里先问清楚对方指哪一种）：

1. **引擎内的子模块**：同一套运行时里拆出的专用能力，例如 **Planner（拆任务）**、**Retriever（RAG）**、**Tool Runner（执行与回灌）**、**Memory Writer（写外存）**——仍是一个 Agent 产品/框架进程内协作。  
2. **与子 Agent（Subagent）混称**：多 Agent 里 **Orchestrator 调度多个专职子 Agent**（探索代码、写补丁、跑测试），每个子 Agent 自己也可以被口语化成「一个 subengine」。

和你篇里 **§2 自上而下那条链** 的对应关系：**Engine ≈ 编排器 + 工具执行 + 记忆 + 护栏 的整体运行时**；**Subengine ≈ 其中可替换/可插拔的一块（或专职子 Agent）**。

### 2.1 ReAct 一步里数据长什么样（和「只聊天」区分）

一轮循环固定四元组语义：**Thought（可选明文）→ Action（tool 名+JSON 参数）→ Observation（宿主执行返回）→** 再回到模型生成 **最终对用户回复或下一轮 Thought**。

**Observation 必须进上下文**：否则模型 **看不到工具结果**，下一拍只能瞎编。宿主侧要对 observation **截断、脱敏、结构化**（只给摘要字段），避免 **token 窗被原始 JSON 撑爆**。

**终止条件**：**最大轮数**、**总 tool 预算**、**无新信息增益**（连续两轮 observation 哈希相同）、或 **用户显式结束**——写不进代码就会在长任务里 **死循环烧配额**。

## 2.2 Agent 推理模式：ReAct、Plan-and-Execute、Reflection（并列还是嵌套？）

三者都是 **「怎么组织 LLM 多步决策」** 的 **模式（pattern）**，不是互斥的三种产品；在工程里常 **组合、嵌套** 使用。

### 各自在干什么

| 模式 | 核心循环 | 典型输出 |
|------|----------|----------|
| **ReAct** | **Thought → Action(tool) → Observation** 交错，每步现想现做 | 边想边调工具，适合 **探索型** 任务 |
| **Plan-and-Execute** | **先出完整计划**（步骤列表），再 **按步执行**；失败可 **重规划** | 计划可审、步数可控，适合 **步骤清晰** 的任务 |
| **Reflection / Reflexion** | 执行一轮后 **自我批评**（哪里错、缺什么），再 **修正重试** | 从失败中改策略，适合 **可验证对错** 的任务 |

### 并列还是嵌套？——面试标准答法

- **概念上并列**：都是 **单 Agent 推理策略** 库里的不同 **控制流模板**，没有谁「包含」谁。  
- **系统里常嵌套**：例如 **外层 Plan-and-Execute**（先列 5 步），**每一步的内层跑 ReAct**（该步里多次查库、改代码）；**每步结束或整轮结束** 再跑 **Reflection**（根据测试结果写 critique，决定是否 replan）。  
- **与 LangGraph 的关系**：LangGraph 是 **运行时**；ReAct/Plan/Reflect 是 **node 里写的策略**。常见图：`Planner node → Executor(ReAct 子图) → Verifier → Reflection → 条件边回 Planner`。

```text
用户任务
  → [Plan] 生成步骤 1..N
  → 对每一步:
        [ReAct 子循环] thought/action/obs 直到该步完成
        [Verifier] 检查
        若失败 → [Reflection] 写原因 → 回到 Plan 或重试该步
  → 汇总输出
```

**和纯 ReAct 的取舍**：ReAct **灵活但贵**（每步一次大模型调用、上下文涨得快）；Plan-Execute **省调用、可审计**，但计划过时需 replan；Reflection **提高成功率**，但多一轮模型开销。

### 面试怎么答

「三者是并列的推理模式，生产里常嵌套：Plan 定骨架，步内 ReAct 探索，Reflection 根据验证结果纠偏；LangGraph 负责把这些模式挂到图上并做 checkpoint。」

## 3. 高效上下文维护

**分层**：  
- **窗内工作记忆**：最近对话 + 本轮工具结果摘要；设 **硬 token 预算**。  
- **异步摘要**：超长就 **后台压摘要**。  
- **长期向量记忆**：按任务检索注入，别全塞。  
- **结构化状态**：订单号、文件路径放 **数据库**，别让模型「口头记住」。

**工程习惯**：工具原始输出 **先裁剪/结构化** 再进窗；重复文档 **hash 去重**。

### 面试怎么答

「分层 + 预算 + 摘要 + 外存检索；大块工具输出别原文塞满窗。」

---

## 4. 主流上下文长度：标称、成本、和 RAG 的关系

### 4.1 「上下文长度」指什么

模型 **单次 forward** 能处理的 **token 序列上限**（输入+已生成），由 **架构、位置编码外推、显存** 共同决定。产品页的 **8k / 32k / 128k / 1M** 是 **这个上限的营销/技术标称**。

### 4.2 标称 ≠ 全程同样好用

即使能塞满 128k：

- **成本**：attention 与 KV 随长度 **增长**，长窗对话 **贵、慢**。  
- **有效利用**：实验与产品反馈里，**极长输入** 仍可能出现 **中间信息利用不足**（needle 类测试）；不能把「能塞进去」等同于「模型一定用上了每一块」。  
- **训练分布**：模型主要在 **较短序列** 上训过，**超长** 行为可能 **不稳定**。

### 4.3 和 Agent / RAG 怎么配合（别二极管）

- **Agent 多轮**：历史对话、tool 结果会 **快速占窗** → 需要 **摘要、外存、RAG 只拉相关 chunk**（§3），而不是每轮 **全文重塞**。  
- **RAG**：海量知识库 **不进权重**；长窗放 **当前任务相关** 的少量证据（详见 **`13` §7**）。  
- **面试一句**：长窗是 **能力上限**；RAG/记忆/摘要是 **在上限内省着用、接外部库**。

### 面试怎么答

「标称长度是单次能处理多长的上限；实际要控成本与利用率，Agent 仍要摘要和 RAG，不是窗越大越好。」

## 5. Tool 调用机制（闭环）

1. 注册工具：**名称 + 描述 + JSON Schema 参数**。  
2. 模型输出 **tool_calls** 结构化字段。  
3. 宿主 **校验 schema → 路由函数**（设超时、权限）。  
4. 结果以 **tool 消息** 回灌对话，再请求模型生成 **用户可见回答**。

**工程要点**：幂等、错误信息压缩回灌、**最大步数**防死循环；多个 **无依赖** 的工具调用可在宿主侧 **并行发起**（不必等前一个 HTTP 返回再发下一个）。

### 5.1 强制 JSON / 结构化输出（从硬到软四层）

Agent、函数调用、评测抽槽都要 **可解析的结构**；只靠「请输出 JSON」在长生成里仍会 **漏括号、加 markdown 围栏、字段类型错**。按可靠性从高到低叠四层（面试常问「怎么保证 tool 参数合法」）：

1. **约束解码 / grammar**：在 **每个 decode 步** 对 logits **mask 掉非法 token**，使采样轨迹 **只能是合法 JSON 串**（OpenAI `response_format: json_object`、vLLM guided decoding、`outlines` / `lm-format-enforcer` 等）。**最强**，但依赖 **推理引擎支持**，且复杂 schema 要维护 **自动机/grammar**。  
2. **JSON Schema 模式**：在 grammar 或 API 层绑定 **字段名、类型、枚举**；比「任意 JSON」更贴业务。  
3. **Prompt**：system 里写 **只输出 JSON、禁止 ``` 围栏、给 1～2 个正例**；成本低，**单独用不够稳**。  
4. **后处理**：括号栈 **截取最外层 `{...}`** → `json.loads` → **Pydantic / jsonschema 校验**；失败则 **把 schema 错误信息喂回模型修一轮**（Repair），或 **拒答/重试**。

**优先级口述**：**grammar > schema 绑定 > prompt > 正则截取**；老模型或引擎不支持约束解码时，才主要靠 **3+4**。

**和 Tool 闭环的关系**：`tool_calls` 的参数段 **必须先过 schema** 再执行；格式错 **不要调真实 API**（防误删、误转账）。与 **§6 Agentic RL** 里 `R_fmt` 一致——格式错可直接 **0 分**。

### 面试怎么答

「Tool = schema + 执行 + 结果回灌；参数用约束解码或 schema 校验兜底，别只靠 prompt 赌模型自觉。」

## 6. Agentic RL：工具调用场景下的 Reward 设计

当 Agent 用 **RL（GRPO / PPO / GSPO 等）** 优化 **「会不会用工具、用得对不对」** 时，奖励不能只有「最终答案对不对」——**中间 tool 轨迹** 要可打分，否则 **credit 分配** 全堆在最后一句，学不动。

### 6.1 Reward 常见分解（可加权求和）

对一条轨迹 `τ`（含多轮 tool call），可设：

```
R(τ) = w_fmt·R_fmt + w_api·R_api + w_lat·R_lat + w_task·R_task + w_cost·R_cost
```

**（1）API / 工具调用成功率 `R_api`**

- **硬约束**：每次 tool 返回 **无异常、HTTP 2xx、schema 校验通过** → +1；**超时、4xx/5xx、解析失败** → 0 或负分。  
- **软约束**：**调用了正确工具**（如该查库却去瞎编）→ 额外加分；**冗余调用**（同一查询重复 10 次）→ 扣分。  
- 面试口径：**「让模型知道只有真正打通 API 才算数。」**

**（2）响应时间 / 延迟惩罚 `R_lat`**

- 记录每次 tool **latency_ms**；超过阈值 `T_max` 扣分，或 `R_lat = -α · Σ max(0, latency - T_0)`。  
- 防止策略学会 **疯狂并行/重试** 刷成功率却拖垮 SLA。  
- 可与 **成功率联合**：又快又对才满分。

**（3）任务结果 `R_task`**

- 最终是否完成用户目标（单元测试、SQL 结果对、订单是否创建）。常作为 **稀疏大奖励**，与中间 shaping 结合。

**（4）格式与可解析性 `R_fmt`**

- tool 参数是否符合 JSON Schema；是否 **必填字段齐全**。Agentic RL 里 **格式错 = 直接 0 分** 很常见。

**（5）成本 `R_cost`**

- **token 数、调用次数、外部 API 计费**；`R_cost = -β · (#calls)` 抑制 **无限 loop 调 API**。

### 6.2 与 GRPO / GSPO 怎么接

- 对同一 **用户 prompt / 任务状态**，采样 **G 条完整轨迹**（含不同 tool 序列），每条算 **标量 `R_i`**（用上式汇总），再 **组内减均值** 得 `A_i`，与 **`12` GRPO/GSPO** 一致。  
- **长轨迹**（多轮 tool + 长 CoT）时，优势估计噪声大 → 更倾向 **GSPO 序列级 ratio** 或 **DAPO 过滤无效组**。

### 6.3 设计注意点

- **稀疏 vs 稠密**：只在最后用任务分，**中间 tool 全 0** → 信用分配难；宜 **每步给 shaping**（这一步 API 成功了吗）。  
- **奖励黑客**：模型可能 **刷无意义但成功的 ping**；要加 **任务相关约束** 与 **调用次数惩罚**。  
- **非平稳**：工具环境变（API 改版）时 reward 分布漂移，需 **重采数据 / 约束策略贴近 SFT**（KL 到参考）。

### 面试怎么答

「Agentic RL 的 reward 要拆：API 是否成功、延迟是否超标、格式是否合法、最终任务是否完成，再加调用成本防死循环；多条轨迹用 GRPO 组内比较，长链可配合 GSPO。」

---

## 本篇小结

- Agent = **LLM + 工具 + 记忆 + 编排 + 护栏**。  
- **ReAct / Plan&Execute / Reflection** = **并列模式**，生产中常 **Plan 外包、步内 ReAct、失败 Reflection**。  
- 上下文 = **预算 + 分层 + 外存**。  
- Tool = **schema + 执行 + 结果回灌**；**强制 JSON** = grammar > schema > prompt > 后处理（§5.1）。  
- **Agentic RL** = **可分解的轨迹级 reward**（成功率、延迟、任务、成本）。
