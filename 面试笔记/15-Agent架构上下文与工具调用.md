# 15｜Agent：上下文、架构、与 LLM 区别、Tool 调用

**建议阅读顺序（本篇内部）**：**Agent vs 裸 LLM**（边界）→ **典型 Agent 架构分块**→ **上下文怎么维护才高效**→ **主流上下文长度数量级**→ **Tool 调用闭环**。

RAG 检索链详见 **`13`**；Prompt 技巧见 **`09`**。

---

## 1. Agent 和 LLM 差在哪

**LLM**：给定文本条件，输出文本分布。  
**Agent**：以 LLM 为 **决策核**，外挂 **工具执行、记忆读写、状态机编排**，形成 **观察→思考→行动** 闭环。

### 面试怎么答

「LLM 是大脑皮层；Agent 是带手脚和记事本、还能调 API 的系统。」

---

## 2. 典型架构（从上到下）

用户入口 → **编排器（orchestrator，状态机/ReAct 循环）** → **策略模型（LLM）** → **工具执行器（HTTP/DB/代码沙箱）** → **记忆子系统（摘要+向量库+KV 状态）** → **护栏与观测**（日志、trace、配额）。

### 2.1 ReAct 一步里数据长什么样（和「只聊天」区分）

一轮循环固定四元组语义：**Thought（可选明文）→ Action（tool 名+JSON 参数）→ Observation（宿主执行返回）→** 再回到模型生成 **最终对用户回复或下一轮 Thought**。

**Observation 必须进上下文**：否则模型 **看不到工具结果**，下一拍只能瞎编。宿主侧要对 observation **截断、脱敏、结构化**（只给摘要字段），避免 **token 窗被原始 JSON 撑爆**。

**终止条件**：**最大轮数**、**总 tool 预算**、**无新信息增益**（连续两轮 observation 哈希相同）、或 **用户显式结束**——写不进代码就会在长任务里 **死循环烧配额**。

---

## 3. 高效上下文维护

**分层**：  
- **窗内工作记忆**：最近对话 + 本轮工具结果摘要；设 **硬 token 预算**。  
- **异步摘要**：超长就 **后台压摘要**。  
- **长期向量记忆**：按任务检索注入，别全塞。  
- **结构化状态**：订单号、文件路径放 **数据库**，别让模型「口头记住」。

**工程习惯**：工具原始输出 **先裁剪/结构化** 再进窗；重复文档 **hash 去重**。

### 面试怎么答

「分层 + 预算 + 摘要 + 外存检索；大块工具输出别原文塞满窗。」

---

## 4. 主流上下文长度（会随产品变）

常见 **8k～128k tokens** 一档；旗舰标 **更长** 甚至 **百万级** 也有宣传。面试加一句：**标称长度 ≠ 全窗都同样好用**，成本与「中间信息衰减」仍要考虑，所以 **RAG 仍常见**。

---

## 5. Tool 调用机制（闭环）

1. 注册工具：**名称 + 描述 + JSON Schema 参数**。  
2. 模型输出 **tool_calls** 结构化字段。  
3. 宿主 **校验 schema → 路由函数**（设超时、权限）。  
4. 结果以 **tool 消息** 回灌对话，再请求模型生成 **用户可见回答**。

**工程要点**：幂等、错误信息压缩回灌、**最大步数**防死循环、可并行工具用 **asyncio.gather**（无依赖时）。

### 面试怎么答

「Tool = schema + 执行 + 结果回灌的闭环；宿主负责超时权限和防循环。」

---

## 本篇小结

- Agent = **LLM + 工具 + 记忆 + 编排 + 护栏**。  
- 上下文 = **预算 + 分层 + 外存**。  
- Tool = **可校验的函数调用接口**。  
- ReAct = **Action + Observation 必须回灌** + **硬终止条件**。
