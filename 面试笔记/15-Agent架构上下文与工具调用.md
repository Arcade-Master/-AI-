# 15｜Agent 上下文维护、主流上下文长度、架构、与 LLM 区别、Tool 调用

对应：**`面试答题.md` 新增**（约第 40～48 行）。

---

## 1. 如何设计一个高效的 Agent 上下文维护方案？

目标：**在有限 token 预算内**，保留 **任务相关** 信息，丢掉 **噪声**，并支持 **多轮工具循环** 不爆窗。

### 分层记忆（推荐口述结构）

| 层级 | 存什么 | 怎么维护 |
|------|--------|----------|
| **工作记忆（in-context）** | 当前任务指令、最近几轮对话、本轮工具入参出参摘要 | **硬预算**：超过阈值则 **摘要压缩** 或 **只保留关键字段** |
| **会话摘要（soft state）** | 用户目标、已确认事实、未完成子任务 | 每 N 轮或 token 超限时 **后台摘要**（异步第二条 LLM 调用） |
| **长期记忆（out-of-context）** | 用户偏好、历史工单、领域知识 | **向量库 + 元数据**；检索时 **top-k 注入** prompt，而非全塞 |
| **结构化状态** | 订单号、文件路径、会话 id | **键值存储 / DB**，不依赖模型「记住」 |

### 效率要点

1. **Token 预算表**：为 system、memory、tools、user、assistant 各划 **上限**；超了先砍 **旧工具原始输出**（保留摘要）。  
2. **工具输出先结构化再进窗**：日志类 **截断 + 关键行提取**；大 JSON **jq 式筛选** 再喂模型。  
3. **去重**：同一文档 chunk 不重复注入；用 **hash 去重**。  
4. **可观测**：每次请求打 **context 组成占比**（便于调阈值）。

## 2. 目前主流模型支持的上下文长度大概多少？

**数量级（会随产品迭代变化，面试答「区间 + 看官网」）**：

- **消费级 API / 开源权重**：常见 **8K～128K tokens** 一档；不少旗舰标称 **128K～200K+**。  
- **长上下文宣传**：部分闭源或新架构标 **1M tokens 级**（实际效果依赖 **长程检索、注意力、价格**）。  
- **工程现实**：**有效利用** 往往短于标称：长文 **中间信息衰减**、**成本**、**延迟** 限制；RAG 仍常用来 **精选片段**。

**面试金句**：报数字时加 **「标称 vs 有效、prefill 价格、是否支持多模态分 token」**。

## 3. 一个完整的 Agent 智能体架构一般包括哪些部分？

可按 **感知 → 规划 → 执行 → 记忆 → 安全** 口述：

1. **用户接口**：Web / IM / API；鉴权与配额。  
2. **编排层（Orchestrator）**：状态机或 ReAct 循环：**读上下文 → 选动作（说/调工具）→ 写回状态**。  
3. **策略模型（LLM）**：生成计划、自然语言、**tool call JSON**。  
4. **工具层（Tools）**：HTTP、DB、代码执行、检索、工单系统；**schema + 实现 + 超时 + 幂等**。  
5. **记忆子系统**：见第 1 节分层。  
6. **检索（RAG）**（可选）：向量库、混合检索、rerank。  
7. **观测与评估**：日志、trace（OpenTelemetry）、离线评测集。  
8. **护栏**：提示词策略、输出过滤、敏感操作 **人类确认（HITL）**。

## 4. Agent 和 LLM 有什么区别？

| | **LLM** | **Agent** |
|---|---------|-----------|
| **定义** | 单次（或少量多轮）**文本条件生成**模型 | **以 LLM 为决策核** 的 **闭环系统** |
| **输入输出** | 文本 in → 文本 out | 文本 + **环境观测** + **工具结果** in → **动作**（含工具调用）out |
| **能力边界** | 无原生「执行」与「持久状态」 | **工具** 提供执行；**记忆/DB** 提供持久 |
| **失败形态** | 胡编、跑题 | 另加 **工具失败、死循环、状态不一致** |

**一句话**：LLM 是 **大脑皮层**；Agent 是 **带手脚和记事本的大脑**。

## 5. 你了解的 Tool 调用机制是怎样的？

### 训练/对齐侧（为何模型会「调工具」）

- SFT：**对话里嵌入 assistant 的 tool_calls**（JSON 片段）与 **tool role 消息**；  
- 或 RL：**工具执行结果** 作为环境反馈。

### 推理侧（经典 ReAct / OpenAI function calling 流）

1. **注册工具**：每个工具 **name、description、parameters（JSON Schema）** 注入 system 或专用字段。  
2. **模型输出**：模型生成 **结构化 tool_calls**（或 XML/JSON 约定）。  
3. **宿主解析**：校验 schema → **路由到具体函数**（Python / HTTP）。  
4. **执行**：**超时、权限、沙箱**；捕获 stdout/异常。  
5. **回灌**：以 **tool / function 角色** 把结果追加到对话，再 **第二次请求** LLM 生成最终用户可见回复。

### 工程要点

- **幂等**：重复调用不产生灾难副作用。  
- **错误回传**：把 **异常信息压缩** 给模型，便于 **自纠**。  
- **并行工具**：无依赖的可 `asyncio.gather`；有依赖的 **拓扑排序**。  
- **防止无限循环**：**最大步数**、**token 预算**、**重复检测**（同一 tool+args）。

---

## 小结

- **高效上下文** = **分层 + 预算 + 摘要 + 结构化状态**，不是无限塞历史。  
- **Agent** = LLM + **工具 + 记忆 + 编排 + 护栏**；**Tool** = schema + 执行 + 回灌闭环。
