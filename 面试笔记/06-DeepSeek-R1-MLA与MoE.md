# 06｜MoE、MLA、DeepSeek-R1 路线、冷启动

**建议阅读顺序（本篇内部）**：先 **MoE 与 Dense 对比**（「多专家少激活」在说什么）→ **MLA 为何省 KV**（建立在已懂 **KV Cache**，见 `02`）→ 再讲 **R1 这类推理模型在训练管线上的特点** → 最后 **冷启动 SFT 为什么要插在 RL 前**。

## 1. MoE：用「少激活的大参数」换容量

**一句话**：前馈层（FFN）不再是一块大 MLP，而是 **很多个 expert**；每个 token 只被 **门控网络** 送到 **top-k 个 expert** 上算。

**常见误解**：「128 个 expert = 把整模型复制 128 份」——**不是**。  
**共享部分**（每层都有、通常不乘 128）：**Attention、LayerNorm、残差、Router/门控、Embedding、LM Head** 等，只占 **一份**。  
**乘 expert 份数的主要是每层里的 FFN 专家支路**：可以理解为「这一层本来有一块大 MLP 的容量，被拆/复制成 **E 个小 MLP（expert）** 并联」；总参里多出来的大头是 **E 份 expert FFN 权重**，但 **不是 E 份整网**。  
所以 **128 个 expert 确实让 FFN 总参暴涨**，但总量仍落在架构设计里（例如官方标 **~30.5B 总参**），和同档 **dense 几十 B** 仍是 **同一数量级**，不会出现「128×32B」这种天文数。

**相对 Dense 的好处**

- **同样一次矩阵乘的算力预算** 下，可以堆 **更多总参** → **更强记忆/模式库**。  
- 训练上有时表现为：**名义参数量巨大** 但仍可训（依赖实现与并行）。

**代价**

- **路由负载不均** → 少数 expert 打满、别的空转 → GPU 白烧。  
- **all-to-all 通信**、checkpoint 巨大、调试难。

### 1.0 总参大、激活小：推理省还是训练更贵？（和「同总参 dense」对齐口径）

先固定比较对象，否则容易说反：

- **「同总参数量 dense」**：每个 token 前向都要用 **全部权重** 参与 FFN 类矩阵乘 → **单 token 算力 ∝ 总参（量级上）**。  
- **MoE**：总参是 **所有 expert 之和**，但每个 token 只过 **top-k 个 expert** → **单 token 前向算力主要 ∝ 激活子网络**，通常 **远小于** 同总参 dense 的「每 token 全量算」。

**推理阶段**：  
- **算力（FLOPs）**：相对 **同总参 dense**，MoE **单 token 一般更省**（条件计算）。  
- **显存 / 带宽**：**不一定省**——完整 checkpoint 仍含 **全部 expert 权重**；部署上常靠 **多卡 EP 分片、只加载本卡专家、或 CPU offload** 才装得下。decode 时虽只算 top-k，但仍要从显存 **读被激活 expert 的权重块**；是否比同算力的小 dense **更省带宽**，取决于 **专家是否本卡命中、是否大量 all-to-all**。

**训练阶段**：  
- **单 token 前向/反向的有效算力**：仍大致跟 **激活 expert 规模** 走，通常 **仍低于**「同总参 dense 每步全激活」那种暴力算力。  
- **但全局成本往往不低**：优化器状态、梯度缓冲通常覆盖 **全部专家参数**（未在本步被选中的 expert 对本 batch 梯度为 0，但 **显存仍占着**）；再加上 **负载均衡 aux loss、路由通信、capacity 溢出处理**，**工程与显存常数**往往比 dense **重**。因此不宜一句话说「训练远大于同参 dense」——更准确是：**每 token 矩阵算力常省，整体训练栈（显存+通信+实现）常更重**；和同 **激活算力规模** 的小 dense 比，MoE 还多 **存全套专家** 这一笔。

**面试收口**：「MoE 省的是 **每 token 的条件计算**；省不省 **显存** 要看是否分片/卸载；训练难在 **全局专家状态 + 路由与均衡 + 通信**，不是单纯和 dense 比 FLOPs 谁大。」

### 1.0.1 举例：Qwen3-30B-A3B（MoE） vs 同代约 32B dense

以 Hugging Face 卡片的 **Qwen3-30B-A3B** 为例（写作时口径）：**总参约 30.5B**，**每 token 激活约 3.3B**，**128 个 expert、每 token 激活 8 个**。对比 **约 32B、全量激活的 dense**（如 Qwen3-32B 一类，具体以官方卡为准）：

| 负担维度 | 30B-A3B（MoE） | ~32B dense | 口述结论 |
|----------|----------------|------------|----------|
| **权重 + Adam 状态（全参数微调）** | 按 **总参 ~30.5B** 存 | 按 **~32B** 存 | **同一量级**，MoE 通常 **略省 ~5%** 量级，**绝不是「按 3.3B 省一个数量级」** |
| **单 token 前向/反向矩阵算力** | 主要跟 **~3.3B 激活路径** 走 | 跟 **~32B 全激活** 走 | **MoE 常显著更低**；粗口算 **3.3/32≈0.1** 是「FFN 条件计算」的量级感，但 **注意力、LMHead、Embedding** 仍占可观比例，真实差距常落到 **约 1/3～1/6 每 token FLOPs** 这种区间（**须以 profiling 为准**，面试说「数倍量级」即可） |
| **通信与工程常数** | **EP / token 路由 / 均衡 loss** | 相对简单 | 多卡时 MoE **可能吃回部分算力优势** |

**结论**：和「同代 ~32B dense」比，**全参数训练峰值显存**一般是 **MoE 略轻或同阶**，不会出现「激活 3.3B 所以显存也按 3.3B」；**真正拉开的是每 token 算力与吞吐**。「大多少」没有单一倍数：显存接近 1:1，算力侧常见 **数倍**（依实现与是否 EP 瓶颈）。

**演变口述**：稀疏门控 MoE → Switch / GShard 证明大规模可训 → 开源 Mixtral 等 → 闭源大模型普遍 **稀疏 FFN + 共享 attention**；工程上与 **TP、EP（expert parallel，专家并行）** 绑在一起。

**训练技巧（背关键词）**：**辅助负载均衡 loss**、**capacity factor**（每 expert 每步处理上限）、**z-loss 稳门控**、看 **per-expert 直方图**。

### 1.2 负载均衡：训练里常用 trick（不止一个 loss）

- **Auxiliary load-balancing loss（最常见）**：让 **「门控预测的概率分布」** 与 **「本 batch 实际落到各 expert 的 token 流量」** 不要长期错位，防 **routing collapse**（全挤在少数 expert）。实现里常是 **`E · Σ f_e · P_e`** 型或其变体，**系数要小**，否则主任务 CE 被带偏。  
- **Capacity factor**：每个 expert **每步最多吃多少 token**；过小 → **大量溢出/改投** 伤质量；过大 → **负载仍可能不均** 且浪费算力。要 **扫 dev**。  
- **z-loss（门控稳定）**：压门控 logits **无界漂移**，减轻极端 one-hot 路由与数值炸。  
- **Router 侧工程**：**noisy top-k / 温度**（实现名各异）在训练早期 **增加探索**，减轻「一开始就锁死少数 expert」；有的实现加 **router z-loss / auxiliary entropy** 鼓励路由别太极端。  
- **Dropless / token dropping 策略**：有的系统 **不允许丢 token**（通信与调度更重）；有的 **允许溢出丢弃或二次分配**——影响 **吞吐 vs 质量**，面试能说清取舍即可。  
- **数据与 batch**：**域极不均衡** 时，某些 expert 会天然更忙；可配合 **混合数据源、重采样、按域调 capacity**。  
- **观测**：训练日志里看 **per-expert token 直方图、溢出率、各卡耗时**；负载长期一边倒时，先怀疑 **数据/门控初始化/EP 拓扑**，再调 loss 系数。

**与 EP 的关系**：EP 把 expert **分卡** 后，若路由仍极不均衡，会出现 **少数 GPU 打满、其它 GPU 等 token** 的 **假并行**；**负载均衡 loss + capacity + 数据** 要一起调，单靠加卡不解决。

### 1.1 路由在优化里长什么样（能讲清就不算背）

**门控**：每个 token 产生到 E 个 expert 的 logits（或打分），取 **top-k** 得到路由权重 `g_i,e`（常为 softmax 后稀疏）。前向只算被选中的 expert；反向梯度 **按路由权重回传** 到门控与 expert。

**负载均衡 auxiliary loss（典型形态，记结构即可）**：令 `f_e` = 本 batch 中路由到 expert e 的 **token 比例**，`P_e` = 门控对 e 的 **平均概率**。常见一项形如 **`E · Σ_e f_e · P_e`**（或变体），直觉是 **惩罚「路由概率」与「实际流量」长期不一致**——避免所有 token 永远只打 expert0（**routing collapse**）。实现里常乘小系数与主 CE 相加。

**capacity factor**：每个 expert **每步最多处理多少 token**；超过则 **溢出 token 被丢或改投**，是 **吞吐与质量** 的硬开关。

**z-loss（门控稳定）**：对门控 logits 加 **`log^2(Z)`** 类惩罚（Z 为归一化常数相关项），抑制 logits **无界漂移**，减少数值炸与「极端 one-hot 路由」。

### 面试怎么答

「MoE 是条件计算：总参大、每 token 只激活子集；难点是负载均衡和通信；训练要加辅助 loss 防塌缩。」

## 2. MLA：在 KV 上动刀（和 MHA/MQA/GQA 同一桌）

**背景**：自回归 decode 每层每步都要读历史 **K、V**；随 **层数 × 序列 × 头数 × 宽度** 涨，**显存与带宽** 先爆。

- **MHA**：每头自己的 K/V。  
- **MQA**：所有头 **共享** K/V，省缓存，表达力可能掉。  
- **GQA**：折中，多 query 共享一组 KV。

**MLA（思想）**：不直接存完整高维 K/V，而存 **压缩后的潜表示**，用时再 **解压/投影** 回 attention 需要的形状 → **缓存读写都变小**。

**为何不太容易「一下废掉」**：经验上 KV 里 **冗余大**；压缩在 **低秩子空间** 做，配合训练补偿。

### 面试怎么答

「MLA 是 KV 侧压缩缓存；和 MQA/GQA 一样都是为了 decode 少搬显存，但走的是低秩潜变量路线。」

## 3. DeepSeek-R1 一类：在考什么叙事

### 3.1 面试官想听的不是「有个 R1 模型」

公开叙事里 R1 路线强调三件事（以官方技术报告为准，数字别背死）：

1. **行为**：长链 **推理轨迹**（分步、自检、回溯），在 **数学/代码** 等 **可自动判对错** 的任务上拉高 pass@k。  
2. **训练栈**：**冷启动 SFT**（少量高质量推理示范）→ **大规模 RL**（常用 **GRPO 类**，省 critic）→ 可选 **蒸馏** 到小模型、**数据飞轮**（模型生成→筛选→再训）。  
3. **底座**：大参数 + **长上下文** +（DeepSeek 系）**MoE 容量 / MLA 省 KV**，支撑 **很长 CoT** 不爆显存。

### 3.2 为何「推理强」要讲因果（别只背 CoT prompt）

- **SFT 只模仿表面**：学会 **「…」格式**，不保证 **步骤真对**。  
- **RL + 可验证奖励**：对 **最终答案**（单元测试、标准答案）给 **0/1 或连续分**，梯度鼓励 **能过关的推理路径**；允许 **探索** 不同解法（在 KL 约束内）。  
- **长链**：中间步骤错可能导致最后错，RL 在 **整段序列** 上仍有 **信用分配** 难题，所以前面要 **冷启动** 降低探索空间（§4）。

### 3.3 和「普通 Chat 指令模型」差别

| | 普通 Instruct | R1 类推理强化 |
|---|---------------|----------------|
| 主损失 | 人类对话 SFT | SFT 打底 + **RL 占大头** |
| 奖励 | 人标偏好 / 无 | **规则、测试、编译** |
| 风险 | 风格对齐 | **格式钻 reward、过长 CoT** |

细节 loss 见 **`05`/`12`**（GRPO/GSPO）。

### 面试怎么答

「R1 叙事 = 可验奖励的 RL 拉出推理行为，不是只加 CoT prompt；前面冷启动 SFT 稳格式，底座靠 MoE/长文撑容量。」

## 4. 冷启动 SFT：为什么不直接 RL

### 4.1 直接 RL 会出什么事

从 **基座或弱 SFT** 起步做 RL（哪怕奖励是「答案对不对」）：

- **输出分布乱**：长生成 **乱码、重复、中英混杂**，reward 信号 **稀疏**（大多 0 分），梯度 **噪声极大**。  
- **探索空间爆炸**：token 组合无穷，**很少采样到** 一条完整正确推理链。  
- **Reward hacking**：一旦偶尔高分，可能学会 **刷长无用步骤、固定模板骗分**（需 KL 到参考、格式约束）。

### 4.2 冷启动 SFT 在干什么

用 **小规模、高质量** 的「题目 + 标准推理过程 + 答案」做 **行为克隆**（仍是对 **回答段** 算 CE，见 `05`）：

- 教会模型 **可读的分步格式**、**停止符习惯**、**常用推理词汇**；  
- 把策略 **锚在「像样推理」附近**，后续 RL 的 **KL 惩罚** 才有合理参考 `π_ref`；  
- **降低方差**：RL 阶段主要在 **「会写推理的模型」** 上做 **增量改进**，而不是从 **乱码空间** 摸索。

### 4.3 和「只做 SFT 不做 RL」的边界

冷启动 **不能替代** RL：SFT 上限是 **示范分布**；RL 才能 **针对可验任务** 继续 **推高通过率**。面试说：**「SFT 给格式与初值，RL 给任务指标。」**

### 面试怎么答

「冷启动 = 少量优质推理 SFT，给 RL 稳定初值和参考策略；直接 RL 易乱码、稀疏奖励、训飞。」

## 本篇小结

- **MoE** = 容量换工程难度；**每 token 算力常省、全套权重显存未必省**；训练栈常更重。  
- **MLA** = KV 压缩路线。  
- **R1** = 推理目标 + RL + 系统结构叙事。  
- **冷启动** = RL 之前的稳定锚点。  
- MoE 训练 = **主 CE + 负载均衡项 +（可选）z-loss + capacity**。
