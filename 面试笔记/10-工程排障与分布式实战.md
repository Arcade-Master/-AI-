# 10｜多卡异常、OOM、死锁、利用率（实战向）

**建议阅读顺序（本篇内部）**：**OOM 定位**（最常问）→ **NCCL / 通信挂**（集体通信路径不一致）→ **死锁** → **变慢与利用率** → **碎片 vs 真泄漏**。  
并行原理请先有 **`04`** 基础，本篇只讲 **「坏了怎么查」**。

---

## 1. CUDA OOM：从栈反推到「是状态还是激活」

1. 看 traceback **爆在 forward 还是 backward**（backward 常是 **激活峰值**）。  
2. **二分**：减 `batch` 或 `seq`，或开/关 **gradient checkpointing**，看峰值是否随 **L²** 变化（提示注意力矩阵）。  
3. `torch.cuda.max_memory_allocated()` 分阶段打印。  
4. 推理另查 **KV**。

### 面试怎么答

「先分 forward/backward，再二分 batch/seq，再结合是否物化注意力判断 L²。」

---

## 2. NCCL timeout / 集体通信卡住

**高频根因**：某一 rank **OOM 或慢** → 其他 rank **all-reduce 永远等**；或 **代码路径不一致**（某 rank 少一次 collective）。

**排查**：单卡跑通再扩；`NCCL_DEBUG=INFO`；检查 **eval 是否只在 rank0 却多了一次 barrier**；看超时堆栈。

### 面试怎么答

「分布式 hang，十之八九是某个 rank 没走到同一个 collective。」

---

## 2.1 DDP 梯度对齐：all-reduce 在干什么、和「变慢」怎么挂上

**目标**：每张卡算完本地 batch 的梯度后，要让 **所有 rank 的同名参数梯度一致**（通常取 **平均**），再各自 `optimizer.step()`，否则 **各卡权重分叉**。

**all-reduce**：每个 rank 持有一块向量片段；通信后 **每 rank 都得到全体之和**（再乘 `1/N` 即平均）。PyTorch DDP 默认在 backward 里 **桶（bucket）** 异步触发，与计算 **重叠**。

**ring vs tree（口述）**：**ring all-reduce** 沿环传递部分和，**带宽友好**、延迟随 world 线性涨；**tree / 2D halving** 降低步数、有时 **大集群更占优**。NCCL 会按拓扑 **自动选**；你调的是 **bucket size、网卡、PCIe/NVLink 拓扑**。

**变慢信号**：`nvidia-smi` 上 GPU 利用率 **锯齿**、profiler 里 **ncclKernel** 占比高、**小模型 + 大 world** → 多半是 **通信主导**；对照 **`04`** 里 ZeRO-3 的 all-gather 成本。

### 面试怎么答

「DDP 靠 all-reduce 对齐梯度；ring/tree 是 NCCL 实现细节；慢时看通信占比和 bucket。」

---

## 3. 死锁

除通信不匹配外，还有 **锁顺序反了**、**线程池里再调 CUDA** 等经典坑。处理：**所有 rank 同一顺序进 collective**；别在 backward 里藏 **条件式跨 rank 同步**。

---

## 4. 训练变慢 / GPU 利用率低

顺序查：**DataLoader**（`num_workers`、是否在主线程 tokenizer）→ **同步日志/每步 eval** → **通信占比**（小 batch + ZeRO-3）→ **CPU 预处理**。

### 面试怎么答

「先看是算不满还是数据喂不饱还是通信等太久。」

---

## 5. 显存碎片 vs 泄漏

**碎片**：`nvidia-smi` 还有空闲却分配失败 → **重启**、少乱 `empty_cache`、调 bucket。  
**泄漏**：`max_memory` **随 step 单调涨** 不归 → 查 **全局 list 引用 logits** 等。

---

## 本篇小结

- OOM / hang / 慢：**三类不同问题**，别混成「多卡不行」。  
- DDP：**all-reduce 平均梯度**；慢查 **NCCL 与 bucket**。
