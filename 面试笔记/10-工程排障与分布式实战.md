# 10｜多卡异常、OOM、死锁、利用率（实战向）

**建议阅读顺序（本篇内部）**：**OOM** → **NCCL / 通信** → **死锁** → **变慢与利用率** → **碎片 vs 泄漏** → **AutoResearch（自主实验循环）**。  
并行与 **DeepSpeed/DDP** 见 **`04` §4、§7.1**；对齐 **SFT→RL** 见 **`05` §8**。

---

## 1. CUDA OOM：从栈反推到「是状态还是激活」

1. 看 traceback **爆在 forward 还是 backward**（backward 常是 **激活峰值**）。  
2. **二分**：减 `batch` 或 `seq`，或开/关 **gradient checkpointing**，看峰值是否随 **L²** 变化（提示注意力矩阵）。  
3. `torch.cuda.max_memory_allocated()` 分阶段打印。  
4. 推理另查 **KV**。

### 面试怎么答

「先分 forward/backward，再二分 batch/seq，再结合是否物化注意力判断 L²。」

---

## 2. NCCL timeout / 集体通信卡住

**高频根因**：某一 rank **OOM 或慢** → 其他 rank **all-reduce 永远等**；或 **代码路径不一致**（某 rank 少一次 collective）。

**排查**：单卡跑通再扩；`NCCL_DEBUG=INFO`；检查 **eval 是否只在 rank0 却多了一次 barrier**；看超时堆栈。

### 面试怎么答

「分布式 hang，十之八九是某个 rank 没走到同一个 collective。」

---

## 2.1 DDP 梯度对齐：all-reduce 在干什么、和「变慢」怎么挂上

**目标**：每张卡算完本地 batch 的梯度后，要让 **所有 rank 的同名参数梯度一致**（通常取 **平均**），再各自 `optimizer.step()`，否则 **各卡权重分叉**。

**all-reduce**：每个 rank 持有一块向量片段；通信后 **每 rank 都得到全体之和**（再乘 `1/N` 即平均）。PyTorch DDP 默认在 backward 里 **桶（bucket）** 异步触发，与计算 **重叠**。

**ring vs tree（口述）**：**ring all-reduce** 沿环传递部分和，**带宽友好**、延迟随 world 线性涨；**tree / 2D halving** 降低步数、有时 **大集群更占优**。NCCL 会按拓扑 **自动选**；你调的是 **bucket size、网卡、PCIe/NVLink 拓扑**。

**变慢信号**：`nvidia-smi` 上 GPU 利用率 **锯齿**、profiler 里 **ncclKernel** 占比高、**小模型 + 大 world** → 多半是 **通信主导**；对照 **`04`** 里 ZeRO-3 的 all-gather 成本。

### 面试怎么答

「DDP 靠 all-reduce 对齐梯度；ring/tree 是 NCCL 实现细节；慢时看通信占比和 bucket。」

## 3. 死锁：不只是 NCCL「等不到」

分布式训练里说的 **hang**，多数是 **某个 rank 没走到集体通信**（见 §2）；但单机或多线程里还有 **真死锁**。

### 3.1 分布式：集体通信路径不一致

**典型写法 bug**：

```python
if rank == 0:
    save_checkpoint()   # 只有 rank0 执行
dist.barrier()          # 其他 rank 永远等 rank0 先进 barrier → hang
```

或：**eval 只在 rank0 跑**，却忘了 **其他 rank 也要进同一次 `all_reduce` / `barrier`**。  
**原则**：**所有 rank 代码路径上 collective 次数、顺序完全一致**；`if rank==0` 分支里 **不要** 单独多一次同步。

### 3.2 锁与线程池

- **多线程抢同一把锁**，且 **持锁时调 CUDA**（CUDA 上下文与线程绑定敏感）→ 可能卡死或非法访问。  
- **DataLoader worker** 里错误地 **初始化 CUDA**（应在主进程建 context）。  
**原则**：训练主路径 **单线程驱动 GPU**；日志、checkpoint 用 **rank0 专用线程** 且不与 backward 抢锁。

### 3.3 排查顺序

1. 先确认是 **NCCL timeout** 还是 **Python 无响应**（`py-spy` / `gdb` 看栈）。  
2. 打印 **每个 rank 最后一条 log**，找 **谁停在 barrier 前**。  
3. 临时 **单卡** 排除模型逻辑；再 **2 卡最小复现**。

### 面试怎么答

「hang 优先查 collective 是否各 rank 对齐；其次查 rank0 独分支和锁+Cuda。」

## 4. 训练变慢 / GPU 利用率低

顺序查：**DataLoader**（`num_workers`、是否在主线程 tokenizer）→ **同步日志/每步 eval** → **通信占比**（小 batch + ZeRO-3）→ **CPU 预处理**。

### 面试怎么答

「先看是算不满还是数据喂不饱还是通信等太久。」

## 5. 显存碎片 vs 泄漏

### 5.1 碎片（fragmentation）

**现象**：`nvidia-smi` 显示 **还有几百 MB 空闲**，但 `cudaMalloc` **报错 OOM**。  
**原因**：之前多次 **大小不一的 tensor 分配/释放**，显存池里 **剩很多小洞**，凑不出 **连续大块**（尤其要一次申请大 activation 时）。  
**处理**：**重启进程** 最有效；训练中长期跑可 **固定 bucket 大小**（如 DDP gradient bucket）、少在热路径 **`torch.cuda.empty_cache()`**（只还缓存给驱动、不整理碎片，有时更慢）。推理服务可调 **max_num_batched_tokens** 等减少形状抖动。

### 5.2 泄漏（leak）

**现象**：`torch.cuda.max_memory_allocated()` 随 **step 单调上升**，几个 epoch 后必 OOM，**与 batch 无关**。  
**常见代码原因**：  
- 把 **带梯度的 tensor**  append 进 **全局 list**（每个 step 多挂一张计算图）。  
- **日志里 `.item()` 前误保留 graph**；`loss.backward()` 后未 `zero_grad` 且重复挂 tensor。  
- **验证循环** 忘了 `torch.no_grad()`。  
**排查**：二分注释代码段；看 **哪一步之后 allocated 不再回落**。

### 5.3 和 OOM（§1）区分

| | 碎片/泄漏 | 单次 forward 真太大 |
|---|-----------|---------------------|
| 触发 | 跑久了才炸 / 有空闲却分配失败 | 改 batch/seq 立刻变化 |
| 工具 | `max_memory` 曲线 | 减 seq 有效 |

### 面试怎么答

「有空闲却 OOM 想碎片；step 单调涨想泄漏；改 batch 就变想单次太大。」

## 6. AutoResearch 是什么、流程是什么（Karpathy 2026 一类）

### 6.1 它解决什么问题

传统 ML 研究：**人改 `train.py` → 跑实验 → 看 val 指标 → git 记一笔**。瓶颈在 **人力的尝试次数**。  
**AutoResearch**（如 Andrej Karpathy 开源的 [autoresearch](https://github.com/karpathy/autoresearch)）把 **「改训练代码 + 跑短实验 + 根据指标保留或回滚」** 交给 **AI coding agent**，在 **固定 GPU 时间预算** 内 **自动搜索** 超参、结构、优化器等。

**定位**：不是新训练算法，而是 **用 Agent 做实验编排**；和 **`09` Harness**（生产 Agent 运行时）同属 **「把 loop 自动化」**，但目标是 **research metrics** 而非 **线上用户请求**。

### 6.2 典型仓库分工（以该 repo 为例）

| 文件 | 谁改 | 作用 |
|------|------|------|
| **`program.md`** | **人写** | 给 Agent 的 **研究宪法**：能改什么、优化目标、简洁性偏好、禁止动评测 |
| **`prepare.py`** | **只读/锁** | 数据、tokenizer、**固定评测**（如 val **bpb**） |
| **`train.py`** | **Agent 可改** | 模型结构、lr、batch、优化器、训练 loop——**唯一实验旋钮面** |
| **git** | Agent + 人 | **指标变好 → commit**；变差 → **revert**，形成 **可审计实验链** |

### 6.3 一轮循环流程（面试按步说）

```text
1. Agent 读 program.md + 当前 train.py + 近期 git 历史（哪些改动有效）
2. 提出对 train.py 的 patch（架构/超参/实现）
3. 在单卡上跑固定时长训练（如 ~5 分钟）→ prepare 侧算 val_bpb
4. 若指标优于基线且满足「简洁性」规则 → git commit；否则 rollback
5. 重复 N 轮，形成大量短实验
```

**评价指标**：常用 **验证集 bpb（bits per byte）** 等 **单一、可自动算** 的标量，避免 Agent 在主观指标上 **自说自话**。  
**约束**：只允许改 **`train.py`** → 防止 Agent **改评测作弊**；人也 **锁死数据管道**。

### 6.4 和「用大模型做对齐 RL」的区别

| | AutoResearch | LLM SFT/RL |
|---|--------------|------------|
| 优化对象 | **训练代码/超参** | **模型权重** |
| 奖励 | **val loss 类指标** | **人类偏好/规则/ Judge** |
| 风险 | 过拟合 **短跑**、删除代码 **碰巧 bpb 好** | reward hacking、幻觉 |

### 6.5 面试怎么答、工程启示

「AutoResearch = Agent 在锁定的评测下反复改 train.py、跑短实验、git 保留变体；核心是 **约束搜索空间 + 自动指标 + 版本管理**，不是魔法全自动发论文。」

对你做 **对齐/Agent 岗** 的迁移：**评测脚本锁死、改动面最小化、指标自动回写、失败即回滚**——和 **`09` Verifier、Harness 预算** 同一套工程思维。
